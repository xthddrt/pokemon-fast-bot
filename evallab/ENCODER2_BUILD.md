## 2. Column count and layout

| Block | Cols | Spec §7 estimate |
|---|---|---|
| §1 per-mon × 12 (50 each) | 600 | ~450 |
| §2 per-side × 2 (94 each) | 188 | ~190 |
| §3 relational | 826 | ~140 |
| §4 counterfactual per-mon × 12 (22 each) | 264 | ~150 (with tera) |
| §4 counterfactual per-side × 2 (6 each) | 12 | — |
| §5 global | 15 | ~17 |
| **Total numeric** | **1,905** | **~950** |

**The §7 size table is not achievable from the §3/§4 definitions as written.**
This is the one number that will disappoint: the spec's stated goal was "leaner
than today's 1,863", and the design as specified lands at 1,905 — the same size.
The whole overshoot is one block:

| §3 relational, itemised | Cols |
|---|---|
| KO matrix: 36 pairs × 2 HP versions × 2 directions × 5-way one-hot | 720 |
| speed bit per pair | 36 |
| active speed margin + tie | 2 |
| 16 move-order bits | 16 |
| derived priority flags | 4 |
| per-move priority bracket (12 slots × 4 moves) | 48 |

720 of the 826 are the KO matrix. Levers, in order of cost:

* **one direction instead of two** — `Layout(ko_directions=1)`, −360 cols →
  1,545 total. §3 literally says "all 36 ordered pairs", which is 6×6 in ONE
  direction. Both directions are encoded by default because one direction tells
  the net who *we* kill and never who kills *us*, which cannot be what the
  design intends. **This is an interpretation call and it is flagged, not
  buried** — flip the flag if the literal reading was meant.
* **drop the full-HP version** — another −360 → 1,185.
* **scalar KO count instead of a 5-way one-hot** — −576 → 1,329.

Per-mon is 600 rather than ~450 because §2's "13 capability bools, encoded PER
MON" adds 12 × 13 = 156; §7 appears to have counted them on the side.
Counterfactual is 264 rather than ~150 because §4's per-mon list is 22 columns
when written out (setup present + 5-column boost profile, then at each of +1 and
+2: OHKO count, outspeed count, sweep flag, and a 5-way mons-to-kill one-hot).

### Layout order
`mon0..mon11` (our active, our bench 1-5, their active, their bench 1-5;
canonical, never sorted) · `side0, side1` · relational · `cf_mon0..11` ·
`cf_side0, cf_side1` · global. `enc2.DEFAULT_LAYOUT.names` is the full ordered
list of 1,905 column names.

## 3. Gate 1 — reachable-volatile enumeration

**44 reachable, 63 excluded**, of the engine's 107 `PokemonVolatileStatus`
variants. Every admission carries its evidence and every exclusion its reason in
`REACHABLE_VOLATILES.md`, generated by `rbpool.py` from the format's actual pool
(509 species, 5,851 sets, 349 moves, 60 items, 203 abilities).

**Eleven volatiles that §2 names by hand are NOT reachable** — the move that
causes them is not a gen9 randbats move. They get no column:

> Perish count (`perishsong`), Octolock, Torment, Imprison, Embargo, Aqua Ring,
> Ingrain, Nightmare, Syrup Bomb, Endure, Charge.

Two others in that list survive only through a side door and are worth knowing
about: **Disable** is reachable via the *ability* Cursed Body (the move is not in
the pool) and **Heal Block** via *Psychic Noise* (the move is not in the pool).

Also: §2 gives the charging-move examples as Fly/Dig/Solar Beam/Meteor Beam. Only
**Solar Beam** and **Meteor Beam** are in the pool, so `charging_move_id` has
exactly two reachable values.

**Empirical cross-check.** Of 200,000 labelled states, only 5 distinct volatiles
ever appear (SALTCURE 4.6% of side-states, HEALBLOCK 1.8%, CONFUSION 0.7%,
LOCKEDMOVE 0.5%, ROOST 0.001%) — all 5 are in the reachable set, so the
enumeration has no false negative on real data. It cannot confirm the other 39;
that corpus is one team pair (see §7 below).

**Two more unreachables, found while building §5:** `HARSHSUN` and `HEAVYRAIN`
need Primordial Sea / Desolate Land, neither in the ability pool. They are folded
onto the SUN and RAIN columns (which is what they are, only stronger) rather than
dropped, so an unexpected one can never be silently lost. That is why §5 is 15
columns, not 17. Gravity is likewise dropped: no randbats move or ability sets
it.

## 4. Static per-set-pair damage table (§3)

Built by `dmgtab.build_pair_table()` over every gen9 randbats set.

| | |
|---|---|
| Sets (the format's own `level,item,ability,4 moves,tera` keys) | 5,851 |
| Ordered pairs | 34,234,201 |
| Build time | **10.2 s** (single process, vectorised) |
| Memory / disk | **136.9 MB** (2 × float16 `[5851, 5851]`) |
| Lookup | **6.6 ns/pair** |

**A full all-pairs table is practical — but the encoder does not use it, and
should not.** It is stored as best damage as a fraction of the target's full HP,
which is exactly what the spec asks for, but it is keyed on *set identity*, and
a live state routinely is not any set: items get knocked off or tricked, a mon
terastallizes, HP and boosts move. Resolving a live mon back to a set row is a
lossy match that the table cannot signal.

**The per-battle alternative is what shipped**, and it is the same kernel on the
actual twelve Pokémon: 144 ordered pairs × 4 moves × 5 stat channels × 5 weather
variants, computed once per search in **6.4 ms** (§6). It is exact for the state
in hand, needs no set matching, and its per-leaf cost is identical to the table's
(one gather plus multipliers). The all-pairs table is kept as a build artifact at
`data/enc2/pairtable.npz` for offline analysis.

## 5. Gate 2 — hand-checked relational correctness

37 hand-computed cases, all passing (`enc2_gate.py hand`). Each is a state built
by field-level surgery on a real state string, with the expected value derived by
hand from the damage formula rather than from the code.

* **KO counts** — 35 damage into 100 HP reads exactly 3HKO; the same pair at 30%
  HP reads OHKO *now* and still 3HKO *at full HP*; Normal into Ghost reads
  "never".
* **Speed order** — faster acts first; **Trick Room inverts both the order bit
  and the sign of the speed margin**; paralysis (200 → 100) loses to 150; Choice
  Scarf (150 → 225) beats 200.
* **Priority brackets** — Sucker Punch (+1) wins the move-order bit against a
  250-speed foe; **Prankster** gives a status move +1 and correctly does *not*
  boost a damaging move; **Gale Wings** gives a Flying move +1.
* **The strict sweep conjunction** — a Dragon Dance user that OHKOs all,
  outspeeds all and faces no priority answer reads `sweep = 1`; the flag goes to
  0 when any *one* of the three conditions is broken (an opponent outspeeds it /
  an opponent survives the hit / an opponent holds a priority KO).
* **Mons-required-to-kill** — "never" when nothing on the other side can kill it;
  "1" when one fast mon one-shots it.
* **Setup profile and capabilities** — Dragon Dance reads +1 Atk / +1 Spe / no
  SpA; Stealth Rock + Recover + Rapid Spin + Trick Room light exactly the four
  matching capability bools.

**Fainted-mon handling** (14 cases, all passing): `alive = 0` while
`slot_occupied = 1`; every capability bool reads 0; excluded from the KO matrix
("never"), from sweeps and from setup; counted in `n_fainted_revivable`. An
*empty* slot (maxhp 0) reads unoccupied everywhere and is not counted as
revivable.

**Three real bugs the gates caught, all fixed:**

1. **Priority brackets were masked to damaging moves**, so Prankster — which only
   ever matters on a status move — read 0. Now masked by "move present and
   usable" instead.
2. **poke-engine does not rewrite `types` when a mon terastallizes.** It sets
   `terastallized` and leaves the type list alone, applying the tera type at
   damage time. Reading `types` directly made every KO count against a
   terastallized defender wrong — a 100%-of-damage error against tera'd Steel
   types. The defensive typing is now derived.
3. **`best_revival_target_score` was a constant zero**, because it was read off a
   KO matrix that (correctly) masks out fainted attackers — and the fainted mon
   *is* the subject of that column. It now reads the unmasked damage.

## 6. Gates 3 and 4 — damage validity and cost

### Damage kernel vs live `poke_engine.calculate_damage`

Best active-vs-active damage, move by move, max non-crit roll.

| | labelled corpus | pool-wide synthetic |
|---|---|---|
| comparisons | 350 | 829 |
| relative error, median | **0.34%** | **1.1%** |
| relative error, p90 | 1.8% | 22.5% |
| relative error, p99 | 3.5% | 101% |
| **KO-bucket agreement** (1/2/3/4+/never) | **98.9%** | **92.9%** |
| within 1 HP | 67% | 32% |

The labelled corpus is 13 species; the synthetic corpus samples the whole pool
(all 509 species, 60 items, 203 abilities) and is the honest number. An offender
census over the synthetic corpus finds **no remaining systematic cause** — no
ability, item, move or weather has a >25% error rate at n ≥ 8. The residual is a
long tail of unmodelled minor modifiers, and it costs about 7 KO buckets in 100.

Four fixes moved this from 91% to 93–99% agreement, all worth recording:

* **five stat channels, not two.** The spec's cheap runtime path multiplies static
  damage by boost ratios per leaf, which only works if the static value records
  *which* stats it used. In the randbats pool that is five real cases: normal
  physical, normal special, **Psyshock** (special move, physical defence — 251
  sets), **Body Press** (physical move, user's *Defence* — 162 sets) and **Foul
  Play** (target's Attack — 89 sets). Folding them together made Body Press
  damage 4× wrong under Iron Defense, which is exactly the position the feature
  exists to describe.
* **PP = 0 means the move cannot be used.** It was not checked.
* **weather is dynamic.** Sun/Rain move damage by 50% and change *which* move is
  best, and weather changes inside a search. The static table is therefore built
  once per weather variant (5 of them) and a leaf selects one; without this,
  sun/rain positions were 25% wrong.
* **Supreme Overlord** scales with fainted allies, so it belongs in the dynamic
  half. It was 63% of the residual error on the labelled corpus before it was
  modelled.

### Static vs dynamic cost — the spec's cost rule

| | |
|---|---|
| parse (`llencoder.parse_batch`) | 0.126 ms/state |
| **STATIC, once per search** | **6.38 ms** |
| **DYNAMIC, once per leaf** | **0.137 ms** → 7,325 leaves/s |
| amortised at 10 leaves/search | 0.77 ms/leaf |
| amortised at 100 leaves/search | 0.20 ms/leaf |
| amortised at 1,000 leaves/search | 0.143 ms/leaf |

**The design is affordable.** The relational and counterfactual blocks —
everything the spec was worried about — are in the 0.137 ms dynamic half, which
is well under a network forward pass for a net of this width. The 6.38 ms static
half is paid once per search and is 4% of the per-leaf budget by 1,000 leaves.
Without the split the encoder costs 1.14 ms/leaf, 8× more.

The split is real, not notional: `encode_states(..., share_static=True)` and
`encode_columnar(C, vocab, S=prebuilt)` are the search path, and `StaticCtx`
holds every species/move/item/stat-dependent quantity — the 5-channel × 5-weather
damage table, priority brackets, capability bools, setup profiles, tera
alternatives, base speeds.

### The split is exact, and that had to be proved

`enc2_gate.py split` builds 200 leaves from one root that vary only in HP,
status, boosts, hazards, weather, Trick Room and **which mon is active**, and
asserts the shared-static path reproduces the cold path bit for bit:
**0 of 1,905 columns differ.**

Getting there took a fix worth recording. The static context was first built in
*slot* order, which depends on `active_index` — so it silently decayed the moment
the search switched, which is most of the branching factor. It is now built in
**party** order and mapped to slot order per leaf. That reorder is the reason the
dynamic half is 0.137 ms rather than 0.076 ms; gathering all five weather
variants during the reorder cost 0.355 ms, so the weather variant is selected
first and only the chosen one is reordered.

**The precondition, stated:** the shared context is valid while the twelve
Pokémon, their PP, their disabled flags and their tera state are unchanged.
Terastallizing mid-search makes 18 of 1,905 columns wrong, so the search must
rebuild (6.4 ms) on a terastallization, a PP exhaustion or a new disable. All
three are rare; everything else a search does is covered.

## 7. Constant and dead columns

**Two censuses, because the labelled corpus cannot answer this question.** All
200,000 labelled positions are **one team pair** — 13 distinct species, 3
distinct 6-mon teams. A column that is constant there is usually constant because
of coverage, not design. `enc2_gate.py fuzz` therefore builds pool-wide synthetic
states (real randbats sets, randomised HP/status/boosts/volatiles/hazards/field);
they are never labelled and are not training data.

| | constant columns |
|---|---|
| 10,000 real states (one team pair) | 598 / 1,905 (31.4%) |
| 4,000 pool-wide synthetic states | **39 / 1,905 (2.0%)** |

**The 39 are the real dead weight:**

| Columns | Count | Why |
|---|---|---|
| `mon*.is_active` | 12 | A deterministic function of the slot index — slots 0 and 6 are the actives by definition of the canonical order. This is design rule 3 ("nothing that is a deterministic function of something else encoded") violating itself; §1 asks for it explicitly, so it was kept. **Recommend dropping: −12.** |
| `mon*.slot_occupied` | 12 | Always 1. Gen9 randbats teams are always six. **Recommend dropping: −12** (the fainted/empty distinction is already carried by `alive`). |
| `mon*.toxic_counter` (bench) | 10 | The engine stores the toxic counter per side; only the active can hold one, so the 10 bench slots are structurally zero. **Recommend dropping: −10.** |
| `cap_trick_room` on 2 slots | 2 | Sampling, not design — Trick Room is in the pool. |
| `weather_turns`, `terrain_turns`, `trick_room_turns` | 3 | Artefact of the fuzz generator, which pins all turn counters to 5. Not dead in real play. |

Dropping the 34 recommended columns gives **1,871**. Combined with
`ko_directions=1` it gives **1,511**.

Nothing is out of range: after two fixes (effective stats can be 4× the raw stat
under +6, so they use 2 × `D_STAT`; priority spans −7…+5, not ±5) every one of
the 1,905 columns lies in [−1, 1] across all 14,000 states, with no NaN and no
Inf.

## 8. Assumptions and known gaps

Stated, not hidden. Each is a judgement the spec left open.

1. **Both KO directions are encoded.** §3's "all 36 ordered pairs" is ambiguous;
   see §2 above. One flag reverts it.
2. **KO counts use the maximum damage roll**; the strict sweep conjunction uses
   the **minimum** roll, so a "sweep" flag means a *guaranteed* sweep. The spec
   says the sweep flag should dominate an evaluation, which argues for the
   conservative version.
3. **Post-setup OHKO counts use opponents' current HP.** The full-HP KO matrix is
   the separate intrinsic-matchup view.
4. **Mons-required-to-kill** counts an opponent as able to act if it is faster, or
   holds a damaging priority move, or survives the setup mon's best hit; the
   count is then the minimum number of acting opponents whose damage sums to the
   setup mon's HP, "never" if the total falls short.
5. **A bench Pokémon has no boosts or volatiles of its own** (they belong to the
   active) but does get side-wide effects: Tailwind, screens, weather.
6. **Accuracy is not modelled anywhere.** A 70%-accurate OHKO reads as an OHKO.
7. **Multi-hit moves use their expected hit count** (3.167 for [2,5], 4.5 with
   Loaded Dice). The engine's `calculate_damage` reports one hit; the gate scales
   it to compare like for like.
8. **Protect and Substitute are not modelled in the KO matrix.** They are turn
   state, not a matchup property. The engine reports 0 damage through Protect,
   so those states are excluded from the damage gate rather than counted as
   errors.
9. **Not modelled in damage, measured as residual:** Facade's BP doubling under
   status, the pinch abilities (Blaze/Torrent/Overgrow/Swarm), Analytic, Solar
   Power, and Showdown's 12-bit chained-modifier rounding (this multiplies in
   float64 and rounds once; worst case ~1 HP). `dmgtab.UNMODELLED` lists the 8
   moves treated as zero damage (Counter, Mirror Coat, Beat Up, Final Gambit and
   friends).
10. **`tera_best_value`** is the max over living, un-terastallized mons of
    max(offensive gain, defensive gain) against the opposing active, where a gain
    that converts a non-kill into a kill (or a death into a survival) scores 1.0.
    **`tera_enabled_sweep`** fires when tera converts a non-kill into a kill on
    the active *and* the mon either already sweeps at +1 or holds a setup move.
11. **`free_turn`** is encoded literally as §4 words it — for side S, the residual
    HP fraction of *their* active after S's best move. S's own free turn is the
    other side's column.
12. Reveal bits, tera and weather/terrain turns are all encoded, but the labelled
    corpus is full-information, so every reveal bit reads 0 there. That is a
    property of §6's data plan, which has not been executed.

# 10. The four approved changes

*Measured on the same machine, same corpus, same gate suite as §1–§9. Every
number below is from a clean run of `enc2_gate.py all` plus the two equivalence
scripts described in §10.5.*

| | before | after |
|---|---|---|
| Numeric columns | 1,905 | **1,511** |
| Cost — static (once per search) | 6.4 ms | **5.2 ms** |
| Cost — dynamic (once per leaf) | 0.137 ms | **0.083 ms** |
| Throughput (dynamic only) | 7,325 leaves/s | **12,045 leaves/s** |
| Cold path (static + dynamic) | 1.14 ms/state | **0.66 ms/state** |
| Dead (constant) columns, pool-wide | 39 (2.0%) | **5 (0.3%)** |

## 10.1 Change 1 — the full-HP KO matrix is gone

`Layout(ko_versions=1)` is now the default: the KO matrix is **current-HP only**,
in **both directions** (who we kill *and* who kills us — that was never the thing
being cut). −360 columns.

The rationale is Sally's: "can I kill it now" is what nearly every decision turns
on, and the intrinsic full-HP matchup is largely recoverable from the stats,
types and moves the net already has. `Layout(ko_versions=2)` restores it.

Note the arithmetic differs from §2's lever table, which listed the −360 for the
full-HP version *after* already applying `ko_directions=1`. Keeping both
directions, the KO matrix is 2 directions × 36 pairs × 5 buckets = **360**
columns, and §3 relational falls 826 → 466.

## 10.2 Change 2 — the damage tensor is two 6×6 cross-side blocks

The old tensor was `(n, 5, 12, 12, N_CHAN)`: all 144 ordered slot pairs. **72 of
them are same-side** — our mons "attacking" our mons — and *no column ever read
one*. Half the damage computation was discarded, and the waste was inherited by
every consumer: the +1 and +2 setup counterfactuals, the tera counterfactual, and
all five weather variants.

It is now `(n, 5, 2, 6, 6, N_CHAN)`. Block 0 is side 0 attacking side 1, block 1
is side 1 attacking side 0. The kernel runs
**6 attackers × 4 moves × 6 defenders × 2 directions = 288 move evaluations**
per position per (weather, tera) variant, and no more.

The restructure runs the whole way down. `_sides_of()` splits any `(n,12,…)`
per-mon array into the attacker view and the side-swapped defender view;
`StaticCtx.pair()` reorders block *d*'s attacker axis by side *d*'s slot
permutation and its defender axis by side *1−d*'s; `_channel_damage`, the burn /
screen / Multiscale / Supreme-Overlord multipliers, the KO matrix, the
counterfactual block and the tera block all work in `(n, 2, 6, 6)`. The
counterfactual block is the clearest case: it is per-slot against *that slot's
six opponents*, which is exactly `[block, my slot, opponent]` — it was previously
building a 12×12 opponent mask and masking away half of it.

**This is a pure refactor and it is proved as one** — see §10.5.

One regression found and fixed while measuring. Splitting per dict key inside the
weather loop meant ~100 `_sides_of` calls × 10 (weather × tera) variants, and the
static half runs at **n = 1** (one battle per search), where it is numpy
call-overhead bound rather than FLOP bound — static went *up*, 6.3 → 7.3 ms.
Only the field changes between weather variants, so the kernel's
attacker/defender/move arrays are now built once per tera variant
(`_kernel_inputs`) and reused across all five: 7.3 → 5.2 ms. That is why static
improves by 1.2× and not 2× — halving the element count does not help an
overhead-bound path; removing calls does.

## 10.3 Change 3 — the confirmed dead weight is gone

−34 columns, all three confirmed dead by §7's pool-wide census:

| Dropped | Count | Why |
|---|---|---|
| `mon*.is_active` | 12 | Deterministic function of the slot index |
| `mon*.slot_occupied` | 12 | Always 1 — gen9 randbats teams are always six |
| `mon*.toxic_counter` (bench) | 10 | The engine stores it per **side**; only the active can hold one |

`toxic_counter` was **relocated, not deleted**: it is now `side0.toxic_counter` /
`side1.toxic_counter`, 2 columns instead of 12, carrying identical values.

The pool-wide constant-column census confirms the diagnosis was right: **39 → 5**
dead columns. The 5 that remain are the ones §7 already identified as *not* dead
in real play — `cap_trick_room` on 2 slots (sampling, not design) and the three
turn counters the fuzz generator pins to 5.

Two gate assertions referenced dropped columns and were rewritten against
surviving ones, with no loss of coverage:

* `gate_fainted`'s two `slot_occupied` checks now read `maxhp`, which is 0 only
  for a truly empty slot — the same fainted/empty distinction.
* `gate_hand`'s "KO at FULL hp is still 3HKO" check is replaced by a direct
  assertion that the underlying damage (35 into a 100-maxhp target) is unchanged
  by the defender's current HP, which is the property that check was really
  testing.

## 10.4 Change 4 — the new cost, and what Rust must deliver

| | |
|---|---|
| parse (`llencoder.parse_batch`) | 0.126 ms/state |
| **STATIC, once per search** | **5.156 ms** |
| **DYNAMIC, once per leaf** | **0.083 ms** → **12,045 leaves/s** |
| amortised at 10 leaves/search | 0.599 ms/leaf |
| amortised at 100 leaves/search | 0.135 ms/leaf |
| amortised at 1,000 leaves/search | 0.088 ms/leaf |

**The number Sally asked for: Rust must deliver ~11×.**

Production search runs ~130,000 evaluations/s. At 12,045 leaves/s on the dynamic
half alone, that is **10.8×**. Including the static half amortised over a
1,000-leaf search (0.088 ms/leaf, 11,364/s) it is **11.4×**. Call it **11×**.

Before the changes it was 17.8×. So the four changes bought a 1.65× reduction in
the gap, and the remaining ask of Rust is 11×, not 18×.

Two things that number does not include, stated rather than buried: it is the
*encoder* only — the network forward pass over 1,511 inputs is a separate cost on
the same budget — and the static half must be rebuilt (5.2 ms) on a mid-search
terastallization, PP exhaustion or new disable, which §6's precondition still
governs unchanged.

### The equivalence proof for change 2

Change 2 is a refactor. Any difference is a bug, not an improvement, so it was

## 10.6 Assumptions and scope

1. **Only these four changes.** No other redesign; §8's assumption list stands
   unchanged except that assumption 3 ("the full-HP KO matrix is the separate
   intrinsic-matchup view") no longer has a matrix to refer to — post-setup OHKO
   counts still use opponents' current HP, and the intrinsic view is now the
   net's job to infer.
2. **Dropping the full-HP matrix is an information loss, not a refactor.** It is
   the one change here that is a judgement rather than a proof. Nothing was
   measured about what it costs the net's accuracy, because no training was in
   scope. If it hurts, `Layout(ko_versions=2)` restores it for +360 columns and
   no code change.
3. **Same-side damage is not merely unread, it is not computed.** Anything added
   later that wants a same-side pair (an ally-targeting effect, a self-hit) must
   compute it; it is no longer sitting in the tensor. Nothing in gen9 singles
   randbats needs one.
4. **`debug["dmg_points"]` is still the 12×12 view** the gates index into,
   re-expanded off the hot path with structural zeros in the same-side quadrants.
   `debug["dmg_cross"]` is the real `(n, 2, 6, 6)` tensor.
5. **The ~11× is the encoder only**, measured on this Mac, single process,
   NumPy 2.5 — not a claim about the whole evaluation.

# 11. The fix + speed pass (n = 1)

*Same machine, same gate suite. Everything below is measured; the two estimates
are labelled. The reference for every equivalence claim is `enc2_ref.py`, a
frozen byte-for-byte copy of `enc2.py` as it stood at the end of §10
(sha256 `4c45968029d6ad18`), with its volatile list pinned so that changing
`rbpool.py` cannot move it. `enc2_equiv.py` is the harness.*

**The regime changed, not just the numbers.** §10.4's "~11×" compared a *batched*
throughput against production's unbatched one. `eval_scratch(&State)` is scalar
at every signature and the batched path was measured at +3 % and deleted, so a
leaf is encoded **alone**. At n = 1 the honest starting point was **1,658 µs/leaf**
against a **≈8.4 µs** budget — 197×, not 11× (`ENCODER_PERF.md` §0).

| | §10 (before) | now |
|---|---|---|
| Numeric columns | 1,511 | **1,413** |
| Volatile columns | 44 (2 dead) | **44 (0 dead, different membership)** |
| **Dynamic, n = 1 (the search's regime)** | **1,658 µs/leaf** | **1,146 µs/leaf (1.45×)** |
| Dynamic, batched n = 512 | 83.2 µs/state | **63.7 µs/state (1.31×)** |
| Dynamic work | 700 array ops / 29,117 elem-ops | **407 / 17,962 (−42 % / −38 %)** |
| Static, once per search | 5.22 ms | **2.37 ms (2.20×)** |
| Static rebuilds on tera / new disable / PP | **16.2 % / 2.7 % / 0 % of transitions** | **never** |
| Rust must still deliver | 198× | **136×** |

## 11.1 Change 1 — the volatile enumeration was wrong in four places

An independent audit of `rbpool.py` against the engine's own write sites found
**two misses and two dead columns**, all traceable to one mechanism gap: the
enumerator admitted an ability only when *the ability's name equalled the
volatile's name*, so an ability that sets a differently-named volatile was
**structurally invisible** however common it was.

| | |
|---|---|
| **+ ATTRACT** | ability **Cute Charm** (`genx/abilities.rs:4435-4473`) injects a 30 % ATTRACT secondary on any contact hit, targeting the **attacker**. Carrier: **enamorus**, 2 of 5 sets. The `attract` *move* being out of pool is irrelevant. |
| **+ CHARGE** | ability **Electromorphosis** (`genx/abilities.rs:1736-1756`) grants CHARGE when hit, which **doubles the next Electric move** (`damage_calc.rs:2950`). Carrier: **bellibolt, 4 of 4 sets** — a damage-doubling flag the evaluator was blind to. |
| **− LIGHTSCREEN** | the **volatile** is gen1-only (`choices.rs:9777-9795`, behind `cfg!(feature = "gen1")`); gen9 sets a side condition, already encoded as `side*.light_screen`. Always-zero column. |
| **− REFLECT** | same, `choices.rs:13611-13629`. |

The **mechanism** is fixed, not the four symptoms: `rbpool.ABILITY_CAUSES` is a
new first-class table of *name-mismatched* ability → volatile causes, consulted
unconditionally (unlike `MECHANIC_CAUSES`, which is only a fallback for
volatiles with no other evidence), and `STRUCTURAL_EXCLUSIONS` now carries the
two gen1-only variants with their source lines. Re-running the enumeration moves
**exactly these four and nothing else**: 44 reachable / 63 excluded, before and
after. `REACHABLE_VOLATILES.md` is regenerated (and now preserves the audit
appendix instead of overwriting it). The encoder takes `VOL_COLS` straight from
`rbpool.reachable_list()`, so the new set is wired through with no code change —
verified: `side{0,1}.vol_attract` and `side{0,1}.vol_charge` appear,
`vol_lightscreen` and `vol_reflect` disappear, every other column is untouched.

## 11.2 Change 2 — the +2 setup counterfactual is gone

`ENCODER_PERF.md` §5 priced every candidate cut; the +2 level was the best value
per column lost. **−98 columns** (12 mons × 8, plus `cf_side*.best_sweep_2`) and
one of the three surviving `combine()` calls, its speed recomputation, its
sort/cumsum and its bucket one-hot. Nothing computes +2 and discards it: the
loop bound is `SETUP_LEVELS = (1,)` and the columns do not exist.

*(§5's table said −132 columns. That counted half of the 264-column
counterfactual block, which double-counts the 6 columns — `setup_present` and
the 5-column boost profile — that the two levels share. The true figure is 98.)*

## 11.3 Change 3 — the static context no longer goes stale

§6's precondition was "same twelve Pokémon, same PP, same disabled flags, same
tera state". The last three were the problem: measured over 895 real MCTS
transitions, **tera fires on 16.2 %** and a **new disable on 2.7 %** (Choice lock
and Encore both set `disabled`). At a Rust static cost of 42–127 µs that is
1.1–3.4 µs/leaf amortised for disable alone — **13–40 % of the entire budget** —
and 6.8–20.6 µs/leaf for tera, which is the whole budget and more.

**Disable and PP** — the reason they were static at all is that the old damage
table pre-took the maximum over each attacker's four moves *within each of five
stat channels*. A maximum cannot be un-taken, so one disabled move invalidated
the table. The table is now **per move**: `(n, 5 weather, 2 blocks, 12
attackers, 4 moves, 12 defenders)`. The leaf masks the moves it may use and
takes the maximum itself. This is not a cost — four moves is *cheaper* than five
channels, and it deletes the static's argmax loop entirely.

**Tera** — the attacker's tera state moves its STAB and the defender's moves its
typing (poke-engine does not rewrite `types`; it sets a flag and applies the
type at damage time). Both are now **axes of the table**: the 12 on each mon
axis is 6 party slots × {not terastallized, terastallized}. A leaf indexes
`2 × party_slot + tera_flag`, so the slot permutation and the tera selection are
**the same gather** — tera costs the dynamic half exactly zero, and the +1 tera
counterfactual falls out of the same table (index the tera'd attacker rows). Not
a partial rebuild: **no rebuild**.

Two smaller stale readers went with them. The setup profile's
`where(mv_ok | is_setup, rank, 0)` was the identity (`mv_setup_rank` is already
0 for every non-setup move), so it never depended on disable or PP in the first
place — now stated rather than accidental. `def_tera_mult`'s best-move pick did
depend on disable; it moved into the leaf, where it also stopped computing 72
attacker × defender entries to read 12 (only the two **active** attackers' rows
are ever read).

**Cost of the fix:** the static half's element count rises 253k → **291k** (+15 %,
the four tera combinations) but its *call* count falls far more, and it is
call-bound at n = 1: **5.22 ms → 2.37 ms, 2.20× faster.** The one regression is
the cold path, where the static is paid per state in a big batch: 0.66 →
0.77 ms/state. That is the stated trade, and it buys the removal of a
16.2 %-rate full rebuild.

**Proved, not asserted:** `enc2_gate.py split` now runs twice — the old set
(HP, status, boosts, volatiles, hazards, field, which mon is active) and a
**hard** set where tera, `disabled` and PP all move as well. Both give
**0 of 1,413 columns differing** from the cold path. On that same hard set the
old shared-static path differs from its own cold path on **549 of 1,511 columns**.

## 11.4 Change 4 — the verified structural waste

* **The bench × bench damage quadrant.** `boost12` is written at slots 0 and 6
  and nowhere else, so every defender boost ratio is *exactly* 1.0 off the
  opposing active — this is structural, not the empirical "0 of 400 states"
  finding. The defender ratios are now applied to **one column of six**
  (`_scale_moves`), and the attacker mask is folded into the attacker
  numerator so masking and the attacker boost cost **one multiply between them**.
  The five-channel product that made the quadrant expensive is gone outright.
* **`spread(vol)`** — `np.repeat(vol, 6, axis=1)` inflated (n,2,107) → (n,12,107),
  **1,284 element-ops per leaf**, to read four volatiles on two active slots. It
  and `spread(scond)` are deleted; Tailwind multiplies a `(n,2,6)` view of the
  speed array and the four volatiles multiply its `[:, :, 0]` column. Every
  factor involved is an exact power of two except one, so the reordering is
  bit-identical.
* **The tera counterfactual** reads only the opposing active, so it now combines
  against **one defender**, not six.
* The per-leaf rebuilds of `M`/`SS`/`CM`/`CS`/`G` (~185 dict entries per leaf)
  are resolved once per `Layout`.

At n = 1, **93–95 % of the cost is dispatch**, so the currency is *calls*, not

## 11.7 What Rust must still deliver

| | before | after |
|---|---:|---:|
| numpy, n = 1 | 1,658 µs/leaf | **1,146 µs/leaf** |
| budget | 8.4 µs/leaf | 8.4 µs/leaf |
| **multiple** | **198×** | **136×** |
| dynamic elem-ops | 29,117 | **17,962** |
| **ESTIMATE: straight Rust port at 2–6 elem-ops/ns** | 4.9 – 14.6 µs | **3.0 – 9.0 µs** |
| static elem-ops (once per search, no longer rebuilt) | 253,059 | 291,020 → 48–146 µs |

The 136× is a numpy figure and is *not* what Rust has to beat — 95 % of it is
dispatch that Rust deletes rather than speeds up. The number that transfers is
the elem-op count, and on the same 2–6 ops/ns assumption `ENCODER_PERF.md` §4
justifies, a **straight** Rust port of the new encoder lands at **3.0–9.0 µs**
against an 8.4 µs budget: it clears it across most of the range instead of
missing by 1.7× at the pessimistic end. With §3.1's invalidation tax now
**zero** rather than 8–24 µs/leaf amortised, and the incremental design of §2.3
still unbuilt and worth a further 2–3×, ≤2× is no longer a coin flip.

## 11.8 Assumptions and scope

1. **Only the five approved changes.** No other redesign; §8's and §10.6's
   assumption lists stand, minus the +2 setup level.
2. **Bit-identity is asserted on the columns, not on intermediates.** One
   intermediate did change shape: `dmg_prio` is now the priority of the winning
   **move** rather than of the winning **channel**. They can differ only when
   two moves in different channels deal bit-identically equal scaled damage, and
   only the *sign* of the priority is ever read; 7,000+ states across four
   corpora show no difference in any column. If one ever appears, ordering the
   move axis by (channel, slot) in the static build reproduces the old
   tie-break exactly.
3. **The cold path is 17 % slower per state** (0.66 → 0.77 ms) because the
   static half now computes four tera combinations and the cold path pays it per
   state. The search path — one static per battle — is 2.20× faster.
4. **The static half's memory grew**: the damage table is
   (n, 5, 2, 12, 4, 12) f32 = 5,760 floats per state, against 3,600 before.
   At the default `chunk=2048` the cold path peaks a few hundred MB.
5. **ATTRACT and CHARGE are admitted on engine-source evidence**, not on
   observed play. Neither carries a duration (`VolatileStatusDurations` has no
   field for either), so they are two bit columns.
6. **The n = 1 figures are single-process, `nice -n 10`, NumPy 2.5.1, on a
   machine with other work on it.** `enc2_equiv.py perf` interleaves the before
   and after trials round by round so that drift cannot favour either; the ratio
   is stable at 1.43–1.45× across runs, the absolute numbers move ±10 %.
